Teams that treat security as "get an audit before launch" keep getting exploited, because an audit is a snapshot of one version of the code, and security is a continuous process spanning spec to monitoring. This lesson is that whole pipeline, in order, so you can see where an audit actually fits (near the end, not at the end) and what has to surround it. The organising idea: you can't buy security as a one-time service; you build it as a loop that repeats on every change.

The pipeline, in order

  • Spec and threat model. Write the invariants and trust assumptions first (Unit 5). If you can't state what must never happen, you can't secure it, audit it, or monitor it.
  • Internal review and tests. Unit, fuzz, invariant and fork tests, with coverage of failure paths, not just the happy path (Unit 5).
  • Formal methods. Symbolic execution or model checking for critical math and invariants (Halmos, Certora, Kontrol). Worth it for the core arithmetic that, if wrong, loses everything.
  • Audits. At least two independent firms for anything holding serious value. Fix the findings, then re-review. One audit is a single point of failure.
  • Audit contests (Code4rena, Sherlock, Cantina): many eyes, paid per finding, which surfaces things a single firm misses.
  • Bug bounty (Immunefi): a standing reward sized to the funds at risk, often up to 10% of potential loss, capped. The ongoing incentive for white-hats.
  • Guarded launch. Deposit caps, an allowlist, limited markets, raised gradually. Limit the blast radius while the code is youngest.
  • Monitoring. Real-time detection of anomalous flows, invariant breaks and oracle deviations, with an automatic pause on critical signals.
  • Incident response. A war room, a pause, communication, coordination with exchanges and security teams, and a post-mortem.

Why the order matters

The sequence isn't arbitrary. Invariants come first because everything downstream (tests, formal methods, audits, monitoring) checks against them, if you don't have them, the auditors have to guess your intent. Two audits beat one because the second catches what the first missed. The contest and bounty come after audits because they're most valuable on code that's already had the obvious bugs removed. The guarded launch limits damage while the code is youngest and least battle-tested. And monitoring plus pause is the backstop for everything that still got through, because something always does.

Audits are a snapshot; security is the loop

The single most important reframe: an audit tells you one version of the code was reviewed at one point in time. The moment you ship an upgrade, that snapshot is stale, and the loop has to run again on the new code. Teams that treat the audit as a certificate of safety ("we're audited!") rather than one stage in a repeating process are the ones whose upgrade introduces the bug the audit never saw. Every change re-enters the loop at the top.

Build it

Write the security plan for your capstone (Unit 17): the invariants list, the test types you'll use, the audit budget, the bounty size (as a percentage of value at risk), the launch caps and the schedule for raising them, and three specific monitoring alerts with automatic-pause thresholds. Writing the plan forces the pipeline to be concrete, especially the monitoring thresholds, which teams usually hand-wave and which are what actually catch the live incident. A plan with real numbers is the difference between "we take security seriously" and a security program.
