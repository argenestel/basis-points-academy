Almost everything in this course, from measuring LVR to reconstructing an exploit, starts with getting data off the chain, and the right tool depends entirely on the job. Use an archive node query when you need one historical value, a trace when you need to see inside a transaction, an indexer when you're building a product backend, and bulk extraction when you're doing research. This lesson maps the jobs to the tools so you stop forcing one tool to do everything.

The raw interface: JSON-RPC

  • eth_call: read contract state at a block (needs an archive node for old blocks).
  • eth_getLogs: fetch events in a block range, filtered by contract and topic.
  • debug_traceTransaction: see every internal call a transaction made, not just what it emitted.

Events versus traces

The key distinction for reading the chain: events are what a contract chose to tell you; traces are what actually happened.

When to use which

Events (logs)cheap, structured, indexedbut only what the contract emitted — a bug or an exploit may emit nothing
Tracesevery internal call, even ones with no eventhow you reconstruct MEV and exploits (Unit 18)

If you're building a dashboard of swaps, events are perfect: they're cheap and the contract emits a Swap event for every one. If you're investigating why funds moved in a way no event explains, you need traces, because the interesting internal calls (a sneaky transfer, a reentrant call) often emit nothing (Unit 18).

The tools by job

  • Indexers for products: Ponder (TypeScript, local-first), Envio (fast, multichain), The Graph (subgraphs). Use these when you're building a backend that needs the chain's data queryable in real time.
  • Bulk research: cryo extracts blocks, transactions, logs and traces to Parquet files; query them with DuckDB or Polars. Use this when you want to analyse millions of events locally without a thousand RPC calls.
  • Hosted SQL: Dune, Allium, Flipside. Use these for a quick question you want answered in SQL without any setup.
# cryo + duckdb: daily Uniswap v3 swap count for a pool
cryo logs --blocks 20000000:20100000 --contract 0x88e6...5640 \
  --event-signature "Swap(address,address,int256,int256,uint160,uint128,int24)"
duckdb -c "select date_trunc('day', to_timestamp(block_timestamp)) d, count(*)
           from 'logs*.parquet' group by d order by d"

Beyond EVM

Non-EVM chains have their own interfaces. Hyperliquid exposes an info API and a websocket for order books, trades, funding and vaults (Unit 9's labs use it). Solana is read via Geyser plugins or RPC providers (Units 23, 24). The principle carries over: pick the interface that matches the job, a websocket for live order-book data, bulk extraction for historical analysis.

Build it

Index every swap of one Uniswap v3 pool for 30 days two ways: with Ponder into Postgres, and separately with cryo + DuckDB. Compare the developer time, the run time, and the query flexibility of each. Doing the same job with a product indexer and a research tool teaches you viscerally which is which: Ponder is more setup but gives you a live, queryable backend; cryo+DuckDB is faster to a one-off answer but isn't a product. Choosing wrong, using an indexer for a one-off query or hand-rolling RPC calls for a product, is a common and expensive mistake.
