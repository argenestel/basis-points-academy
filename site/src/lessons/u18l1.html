Every exploit, liquidation and arbitrage is a transaction you can take apart, and learning to do it turns the incident table of Unit 15 from a list of names into a set of concrete, reproducible lessons. This lesson is the investigator's workflow, the same one security researchers use, applied to understanding (and defending against) any transaction. It's reconstruction, not attack: you fork to a past block and replay what already happened, to learn how to prevent the next one.

Four tools

  • Etherscan (and its siblings): verified source code, read/write tabs, internal transactions, event logs, token transfers. The starting point.
  • Phalcon (BlockSec): a fund-flow graph, a full invocation tree with decoded calls, balance changes per address, and state diffs. The fastest way to see what happened in an exploit.
  • Tenderly: a step-through debugger, gas profiler and transaction simulator, plus forks and virtual testnets for replaying with modified state.
  • Foundry: cast run replays a mined transaction locally with a trace; fork tests reproduce it in code (Unit 5).
cast run 0x<txhash> --rpc-url $ETH_RPC --quick          # replay with a call trace
cast call <addr> "getReserves()(uint112,uint112)" --rpc-url $ETH_RPC --block 19000000
forge test --fork-url $ETH_RPC --fork-block-number 16817995 -vvvv   # reproduce in a test

The workflow

  1. Start from the attacker's transaction and read the fund flow first. Who ended up with what? The fund-flow graph (Phalcon) shows the money moving, which orients everything else.
  2. Open the invocation tree. Find the first call where state stopped making sense: a price moving impossibly, a balance check passing that shouldn't have, a donation (Unit 5's inflation attack), a reentrant call (Unit 2).
  3. Read the victim contract's verified source at that function. Now you can see why the state did the wrong thing.
  4. Reproduce it in a Foundry fork test, forking to the block before the attack, as DeFiHackLabs does for hundreds of incidents.
  5. Write the invariant that would have caught it (Unit 5). This is the step that turns an investigation into a defence.

A good first case: Euler, March 2023

Euler (~$197M, later returned) is an ideal first reconstruction. A donation function let the attacker make their own account insolvent, then liquidate themselves at a profit, a self-liquidation enabled by a missing health check after the donation. The rekt post-mortem plus a Phalcon trace teach more than any textbook, because you can follow the exact call where the account's health was supposed to be checked and wasn't. Reproduce it in a fork test, watch the self-liquidation profit appear, and then write the invariant ("an account can never be made insolvent by its own action") that would have failed before the attack. That loop, trace → reproduce → invariant, is the whole skill.

Why this is a defender's skill

Reconstructing exploits is how you learn to prevent them. Every reconstruction ends with an invariant you can now check in your own code (Unit 5, Unit 15). After reproducing a dozen incidents, you recognise the shapes, the donation, the stale price, the missing check, before you write them. DeFiHackLabs is a library of hundreds of these as runnable fork tests; working through them is the single most efficient security education available, and it's all reconstruction of what already happened, on forks, never against live systems you don't own.

Build it

Pick the Euler exploit transaction. Trace it in Phalcon and write a five-step timeline of the attack, replay it with cast run, then reproduce it in a Foundry fork test. Finally, write the invariant that would have caught it. Doing all four, the human-readable timeline, the local replay, the coded reproduction, and the invariant, is how an incident stops being a headline and becomes a lesson you've internalised deeply enough to never ship yourself.
