Execution is where your chain runs code and updates state, and the first decision, which virtual machine, is really a decision about who will build on your chain at all. The rest of this layer, metering, state commitments, storage, parallelism, determines how fast it goes and how it scales. This lesson covers those choices with the trade-offs that actually drive them.

Hyperliquid's answer is instructive: a native order-book engine for speed plus an EVM so third parties can still compose (Unit 2). You don't always have to choose one.

Metering

Any chain that runs untrusted code needs gas (to price scarce resources and bound execution, Unit 2) and per-block resource limits. The key principle carries straight over from Ethereum: price storage writes far above compute, because state lasts forever while compute is transient. A chain that under-prices storage accumulates state it can never afford to store.

State commitments

The state root (lesson 1) has to be computed from the state somehow, and the data structure is a trade-off:

  • Merkle-Patricia trie (Ethereum): flexible, but I/O-heavy (lots of random disk reads).
  • IAVL (Cosmos), Jellyfish Merkle (Aptos), sparse Merkle trees: each trades off proof size, update cost and disk behaviour differently.
  • The modern pattern: flat key-value storage for the actual data (fast reads/writes), plus a separate commitment computation for the root. Reth uses MDBX; databases underneath are RocksDB or MDBX.

Parallelism and performance

Single-threaded execution (the EVM's default) leaves performance on the table. The three main approaches (Unit 2):

  • Declared access lists (Solana): transactions say what they touch, so non-conflicting ones run in parallel.
  • Optimistic re-execution (Block-STM, used by Aptos and Monad): run everything in parallel, detect conflicts, re-run just the conflicting transactions.
  • Ethereum's Block-Level Access Lists (EIP-7928, in Glamsterdam, Unit 4): a path to parallel validation on the EVM.

Alongside parallelism, two operational necessities: state sync and snapshots so new nodes can join without replaying all history, and a plan for pruning and state growth from day one, because state only grows and a chain that never prunes eventually can't be run on commodity hardware.

Build it

Persist your toy chain's state in RocksDB (or sled/pebble), compute a sparse Merkle root over accounts, and add a /proof endpoint that returns a Merkle proof for any balance. Then verify that proof with a separate light-client script that only has the header. Building the proof endpoint and a client that trusts only the state root is the moment the state root from lesson 1 earns its keep: you've made your chain verifiable by something that isn't a full node, which is the foundation of light clients and bridges (Unit 12).
