Strip a blockchain down to its cryptography and you find three primitives doing almost all the work. Hashes commit to data and chain blocks together. Signatures prove who authorised what. Merkle trees prove that a piece of data is part of a larger set without revealing the whole set. Every light client, every bridge, every airdrop claim is built from these three. This lesson is the working engineer's version: what each one guarantees, which variant to use, and the replay bug that keeps costing bridges money.

Hashes: commitment and chaining

A hash function (SHA-256 in Bitcoin, Keccak-256 in Ethereum) maps any input to a fixed-size digest, with three properties: you can't find two inputs with the same output (collision resistance), you can't reverse it (preimage resistance), and a tiny input change scrambles the whole output (the avalanche effect). Blocks commit to their parent's hash and to their contents' hash, so the chain is literally a chain: change any past block and its hash changes, which changes the next block's parent reference, which changes its hash, and so on to the tip. That's why "tamper-evident" is free: rewriting history means recomputing every block after the change.

Signatures: three schemes, three jobs

A signature proves that whoever holds a private key authorised a message, without revealing the key. Three schemes dominate, and each exists for a reason.

BLS aggregation is why Ethereum can have hundreds of thousands of validators attesting every slot without the data exploding: many signatures over the same message collapse into a single signature that verifies against the combined public key.

Replay protection: the bug that keeps biting

A signature authorises a message. If the message doesn't say which chain, which contract, and which time it's valid for, the same signature can be replayed somewhere it wasn't meant to go. The defences:

  • Chain id (EIP-155): a signature for mainnet shouldn't be valid on a testnet or a fork.
  • Nonce: a per-account counter so a signature can't be used twice.
  • Domain separation (EIP-712): for off-chain signatures, bind the signature to a specific contract, chain and purpose, so a signature meant for one protocol can't be replayed against another.

Why this is in the first cryptography lesson

Signature replay across chains caused real bridge losses, including a reported ~$127M cross-chain incident in June 2026. The pattern recurs because it's easy to sign "withdraw 1,000 to Alice" and forget to also commit to "on this chain, through this contract, with this nonce, once." Unit 12's bridge and the wargame's challenge 5 are both this bug. Learn the four things a signature must commit to now, and you'll recognise its absence everywhere: recipient, nonce, chain id, contract address.

Merkle trees: proving inclusion cheaply

A Merkle tree hashes data in pairs, up a tree, to a single root. To prove that one leaf is in the set, you don't reveal the whole set; you reveal just the sibling hashes along the path from the leaf to the root (log₂(n) of them), and the verifier recomputes the root. If it matches the trusted root, the leaf is proven to be included.

def merkle_root(leaves):
    layer = [keccak(l) for l in leaves]
    while len(layer) > 1:
        if len(layer) % 2: layer.append(layer[-1])     # duplicate the last if odd
        layer = [keccak(min(a,b) + max(a,b))            # sorted pairs: OpenZeppelin convention
                 for a, b in zip(layer[::2], layer[1::2])]
    return layer[0]

This is the trick behind airdrop claims (prove your address is in the list), light clients (prove a transaction is in a block given only the block's root), and bridges (prove an event happened on chain A given only A's state root). Ethereum uses a Merkle-Patricia trie for its state, a richer structure, but the idea is the same: commit to everything in one root, prove any part with a short path.

Build it

Implement a Merkle tree with proof generation in Python or TypeScript, then write a Solidity contract that verifies the proofs with OpenZeppelin's MerkleProof, and fuzz-test it in Foundry (Unit 5): for any leaf in the set, a correct proof verifies; for any leaf not in the set, no proof does. Getting the sorted-pair convention to match between your generator and OpenZeppelin's verifier is the exercise, and it's exactly the kind of cross-tool detail that, gotten wrong, bricks an airdrop or a bridge.
