Cross-chain messaging protocols all solve the same problem (convince chain B of an event on A, lesson 1) but differ in what does the verifying and, crucially, in who chooses the verification. That last point is the one that caused 2026's biggest hack: when a protocol lets each application configure its own security, a lazy or default configuration becomes the application's vulnerability, not the protocol's. This lesson compares the major messaging layers through that lens.

Two families emerge. IBC is natively verified (light clients, the strongest model from lesson 1). The rest are externally verified, differing in whether the verifier set is fixed (Wormhole's guardians, Axelar's validators) or configurable by the app (LayerZero's DVNs, Hyperlane's ISMs).

Configurable security means configurable failure

The app-configurable model (LayerZero, Hyperlane) is powerful: a well-resourced app can choose a strong, defence-in-depth stack. But it also means the app owns the security decision, and a weak default is a weak bridge.

KelpDAO's rsETH bridge, April 2026

Kelp's rsETH bridge on LayerZero ran with a 1-of-1 DVN configuration: a single verifier attesting to cross-chain messages. An attacker reportedly poisoned the RPC nodes that single DVN relied on and DDoS'd the clean ones, so the DVN signed a forged message, and about 116,500 rsETH (~$292M) was minted from nothing (Unit 7, Unit 15). Afterwards LayerZero said it would stop signing for 1-of-1 configurations, and Kelp disputed whether 1-of-1 had effectively been the documented default. The protocol worked as designed; the configuration was a single point of failure. The lesson is stark: when security is configurable, the configuration is the security, and a default nobody changed can be a default that drains the bridge.

The rule of thumb for your app

If you deploy on an app-configurable messaging layer, the burden is on you. The defensive baseline:

≥ 2 independent verifier sets (different operators, infrastructure, codebases) + rate limits per time window + a pause guardian + monitoring that compares source and destination supply, alerting within one block

Two independent verifiers so that compromising one isn't enough. Rate limits so that even a full compromise is bounded. A pause so a human (or a monitor) can stop it. Supply monitoring so you know within a block if minted exceeds locked.

Defence in depth is the whole idea: no single verifier, no single codebase, no single infrastructure provider should be able to forge a message, and even if one somehow can, the rate limit and pause bound the damage. CCIP builds some of this in (the separate Risk Management Network is a second, independent check); on LayerZero or Hyperlane you have to assemble it yourself.

Build it

Deploy a LayerZero OApp (or a Hyperlane app) between two testnets, configure it with two required DVNs or ISMs, and then write a test plan for what happens if one verifier signs a forged message: does the second catch it, does the rate limit bound it, does the pause work? Building the two-verifier config yourself, and then simulating one going rogue, is the exercise that would have prevented KelpDAO. Configurable security is only as good as the person who configures it, and that person is you.
