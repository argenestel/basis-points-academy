The HTTP status code 402 Payment Required sat unused for decades, waiting for a form of money that could be sent as easily as an HTTP header. Stablecoins are that money, and x402 revives 402 to let any client, including an AI agent, pay for a resource per request, with no account and no API key. This lesson is how x402 works and, more importantly, the security an agent that holds money and reads untrusted content absolutely requires.

How x402 works

x402 (launched by Coinbase in 2025) uses the 402 status to negotiate a payment inline with the request:

1. client → GET /data 2. server → 402 + payment requirements (amount, asset e.g. USDC, network, payTo) 3. client signs a payment (e.g. EIP-3009 transferWithAuthorization) → retries with an X-PAYMENT header 4. server (or a facilitator) verifies and settles on-chain → 200 + the data

No account, no API key, and payments as small as fractions of a cent on cheap chains. The payment is a signed authorization carried in a header.

The x402 Foundation (Coinbase and Cloudflare) stewards the standard, and 2026 reports describe a move to the Linux Foundation and integrations by Google's AP2 and payment companies. Adoption numbers in 2026 vary widely by source, so treat them as rough. The significant thing isn't the adoption figure; it's that machine-to-machine micropayments, long promised, now have a working standard, which matters a lot as AI agents start transacting.

The security an agent wallet needs

An AI agent that holds a wallet and reads untrusted content is a new and dangerous combination, and x402 makes it concrete. The defences aren't optional:

Agent-wallet security requirements

Spend limits and session keysan agent should never hold an unlimited key (Unit 5)bounds the damage of any compromise or mistake
Prompt-injection defencescontent the agent reads can try to make it pay or approve somethingrequire allowlists and human confirmation above a threshold
Replay protection and expiryin the signed authorizationsa captured payment authorization can't be reused (Unit 2)
A refund and dispute pathfor when a paid request failsthe agent paid but didn't get the data

Prompt injection is the new attack surface

The genuinely new risk: an agent reads web content to decide what to do, and that content is untrusted (Unit 18's "frontend is attack surface," generalised). A malicious page can contain text designed to make the agent pay an attacker, approve a transfer, or exceed its budget, a prompt-injection attack aimed at the agent's wallet. The defences are the session-key scoping of Unit 5 (the agent's key can only do bounded things), allowlists of who it can pay, and human confirmation above a spend threshold. An agent with an unlimited key that pays based on content it reads is a drainer waiting for the right page, which is why spend limits and injection defences are the first thing to build, not the last.

Build it

Using the coinbase/x402 examples, put a paid endpoint in front of your funding-collector lab's data (0.001 USDC per call on a testnet), and write an agent client with a daily spend cap. Building the spend cap into the agent client is the point: you'll see how easy it is to make an agent pay (a few lines) and how deliberate you have to be to make it pay safely (the cap, the allowlist, the confirmation threshold), which is the security-first mindset every agent-payment system needs before it touches real money.
