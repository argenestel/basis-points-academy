The reason onchain trading feels worse than a centralised exchange isn't the matching or the fees; it's that every action needs a wallet popup and a gas payment in the native token. Account abstraction fixes this by making accounts programmable: they can validate with any rule you like, pay gas in any token, batch actions, and delegate narrow permissions to a session key. This lesson covers the two mechanisms (4337 and 7702) and the security rules that come with giving accounts this much power.

ERC-4337: smart accounts without a fork

4337 adds smart-contract wallets as a layer on top of Ethereum, with no consensus change, through a parallel mempool.

  • Users sign a UserOperation (an intent to act) instead of a raw transaction.
  • Bundlers collect UserOperations and submit them to a singleton EntryPoint contract.
  • The EntryPoint calls each account's own validation logic, which can implement any signature scheme: a passkey, a multisig, a session key, a social-recovery rule.
  • Paymasters can sponsor the gas, or accept gas payment in an ERC-20, so the user never needs ETH.

The key shift is that "is this transaction authorised?" is no longer hard-coded to "is it signed by this one private key?" It's whatever the account's code says. That's what enables everything below.

EIP-7702: EOAs gain code

4337 needs you to use a new contract-wallet address. EIP-7702 (shipped in Pectra, May 2025) lets your existing EOA delegate to contract code while keeping its address. You sign an authorisation that says "for my account, run this code," and your EOA gains batching, sponsorship and scoped permissions without migrating. For protocol builders this is both a gift (every user can now have smart-account features) and a trap, discussed below.

Session keys are the big one for trading. Hyperliquid's "API wallets" (agent keys) are the same idea built natively: a key scoped to trading that can't withdraw funds. The whole point is to approach CEX responsiveness without custody.

The security rules

Programmable accounts change assumptions that a lot of existing code relied on, and getting these wrong is how account abstraction becomes a vulnerability.

  • Scope session keys tightly. A session key must be able to do exactly one narrow thing and nothing else. The build exercise is to prove, with tests, that a trading session key cannot withdraw funds, no matter what it's asked to do. A session key that can be tricked into a transfer is a hot wallet with a UI.
  • Never rely on tx.origin. Code that assumed tx.origin == msg.sender means "an EOA, not a contract" is now simply wrong: after 7702, an EOA can run contract code, and onlyEOA checks based on tx.origin no longer mean what they used to. Treat every caller as potentially a contract.
  • Assume msg.sender can be a contract. Reentrancy, callback and approval logic all have to hold when the caller is a smart account that can do arbitrary things in its validation or execution.
  • Support EIP-1271. A smart account can't produce an ECDSA signature the way an EOA does; it validates signatures by calling its own isValidSignature. Any protocol that checks signatures (permits, orders, votes) must support EIP-1271 or it silently excludes every smart-account user.

The 7702 re-audit

EIP-7702 means a one-line assumption buried in old code (require(tx.origin == msg.sender) as a proxy for "no contracts allowed," often used as a flash-loan or sandwich guard) is now a false assumption across the whole ecosystem. If your protocol has such a check, it no longer does what you think. After Pectra, re-audit every place you distinguished EOAs from contracts; the distinction has largely dissolved.

Build it

Build a session-key module: a smart account that lets a secondary key call only placeOrder() on a single market, with a notional limit and a 24-hour expiry, and prove with tests that this key cannot withdraw funds, call other contracts, or exceed its limit. The test that the key can't do things is more important than the test that it can. That inverted emphasis, proving the absence of a capability, is the security mindset from lesson 1 applied to access: you're writing the invariant "a session key never moves funds" and then trying to break it.
