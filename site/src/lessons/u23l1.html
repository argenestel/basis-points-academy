Solana's programming model is different enough from Ethereum's that EVM intuitions actively mislead you. The core inversion: on Ethereum a contract owns its storage; on Solana programs are stateless and all state lives in separate accounts. Once you internalise that and its consequences, declared account access, PDAs, CPIs, the rest of Solana development follows. This lesson is that model, with a translation table from EVM so your existing knowledge transfers instead of fighting you.

Stateless programs, state in accounts

On Ethereum, a contract and its storage are one thing. On Solana, they're separate: programs are stateless code, and all state lives in accounts that programs own.

account = { lamports, data: bytes, owner: program id, executable: bool } only the owner program may change data or debit lamports; anyone may credit lamports accounts must hold a rent-exempt minimum balance proportional to their size (max 10 MiB)

A program reads and writes data in accounts it owns. The same program can own many accounts, and the accounts, not the program, hold the state.

PDAs and CPIs

  • PDAs (program-derived addresses): addresses derived deterministically from seeds plus the program id, chosen to be off the ed25519 curve so no private key exists for them. Programs use PDAs for deterministic state (e.g. ["curve", mint] gives the curve account for a given mint) and to "sign" for themselves via invoke_signed. A PDA is how a program controls an account without a keypair.
  • CPIs (cross-program invocations): calling another program, for example invoking the Token program to mint tokens, passing it the accounts it needs. The Solana analogue of a contract calling another contract, but with explicit account passing.

Why transactions declare their accounts

Every Solana transaction lists every account it will read or write, up front. This isn't bureaucracy; it's what enables parallelism. Because the runtime (Sealevel) knows which accounts each transaction touches, it can run any two transactions that don't share a writable account in parallel (Unit 2). The cost is that a hot account, a popular pool or mint that many transactions want to write, becomes a serialisation bottleneck, which is why Solana design (Unit 23 lesson 4, Unit 24) is largely about sharding state to avoid hot accounts.

The limits that shape design

  • Transactions are capped at 1,232 bytes.
  • 200k compute units per instruction by default, 1.4M per transaction.
  • Address lookup tables (versioned transactions) let you fit more accounts into a transaction.

These limits are tighter than they first seem and drive real design decisions, a complex instruction touching many accounts can hit the transaction-size or compute limit, forcing you to split it.

The EVM translation

Translating EVM concepts to Solana

Contract storage→a set of program-owned accounts
A mapping (key → value)→a PDA per key
msg.sender→a signer account
A token balance→a token account
"Calling a contract"→a CPI with explicit accounts

This table is the bridge. When you'd reach for a mapping in Solidity, you create a PDA per key on Solana. When you'd check msg.sender, you require a signer account. Keeping the translation in mind lets your EVM experience accelerate rather than confuse your Solana learning.

Build it

In the solana-launchpad lab, find where the curve PDA is derived, where it signs a CPI (mint_to), and where lamports move directly. Draw the accounts each instruction touches and mark them read or write. Tracing the PDA derivation and the CPI signing in real code, and drawing the account-access map, is how the stateless-program model stops being abstract: you see the program controlling the curve account via a PDA, signing a mint via CPI, and declaring exactly which accounts each instruction locks, which is the foundation for everything in Units 23 and 24.
