Ethereum calls itself a world computer, and the metaphor is exact: it's a single shared machine that anyone can run code on, where the code is deterministic, the memory is persistent, and every operation is metered and paid for. Understanding how that machine charges for work, and why storage is the thing it charges most for, shapes how you write every contract. This lesson is the EVM from an engineer's seat.

The account model

Unlike Bitcoin's UTXOs (lesson 2), Ethereum has accounts. Two kinds: externally-owned accounts (controlled by a private key) and contract accounts (controlled by code). Each has a nonce and a balance; contracts also have code and storage. The entire state is one big map from addresses to accounts, and every block commits to the whole thing via a state root (a Merkle-Patricia trie root, lesson 1). That commitment is what lets a light client prove any balance with a short proof.

The EVM: a metered stack machine

The EVM is a stack machine with 256-bit words, volatile memory (wiped each call), persistent storage (survives), and read-only calldata. It's deterministic and single-threaded: the same inputs always produce the same result, which is what lets thousands of nodes agree. Every opcode costs gas, and gas does two jobs: it prices scarce resources, and it sidesteps the halting problem (a program can't loop forever because it runs out of gas and reverts).

What different operations cost (order of magnitude)

Arithmetic (ADD, MUL)a few gascompute is cheap
Memory accesslow, grows with sizevolatile, so cheap
Cold storage read (SLOAD)2,100 gas since EIP-2929touching a new slot costs extra
Fresh storage write (SSTORE)20,000 gasthe expensive one: state lasts forever

The pattern to internalise: compute is cheap, storage is dear, and the first touch of anything is dearer than later touches. A fresh SSTORE costs roughly ten thousand times an ADD. That ratio drives contract design.

Why storage dominates design

Every value you write to storage is paid for once at write time and then stored by every node, forever. So the single most effective gas optimisation is writing less state. Pack multiple small variables into one 256-bit slot. Use events (cheap, not stored in state, Unit 16) for history you only need to read off-chain, rather than storage. Avoid per-user storage where a global index will do (the index-accounting trick from Unit 7). A contract that writes a storage slot per user per interaction is a contract whose users pay a tax forever; one that uses a single global accumulator is not.

EIP-1559: fees that behave

Before 2021, gas was a blind first-price auction (Unit 1): you guessed a price and overpaid or got stuck. EIP-1559 replaced it with a posted price that adjusts algorithmically.

price paid per gas = min(base fee + priority tip, maxFeePerGas) base fee adjusts up to ±12.5% per block toward a 50%-full target base fee is BURNED; the priority tip goes to the proposer

You submit a max you're willing to pay and a tip; you pay the base fee (whatever it is) plus your tip, never more than your max. No guessing a clearing price.

Two consequences worth knowing. Fees now rise smoothly rather than chaotically, because the base fee can only move 12.5% per block. And because the base fee is burned rather than paid to the proposer, ETH can be net-deflationary when usage is high, and the proposer has no incentive to stuff the block with their own transactions to inflate fees (Unit 1's mechanism-design reasoning).

Why this matters for protocol design

  • Every storage write is a permanent cost to your users. Design compact state from the start; it's much harder to fix later.
  • Rollups post their data to Ethereum, and since EIP-4844 that data goes in blobs with their own fee market (Unit 4). Your L2 users' costs track blob fees, not calldata gas.
  • Composability is the superpower and the attack surface. Synchronous calls between contracts in one transaction are what make flash loans, aggregators and liquidations possible (Units 6, 7). They're also what make reentrancy and flash-loan attacks possible (Units 5, 15). The same property enables both.

Build it

In Foundry, write a contract that stores 100 values unpacked (one per slot), then a version that packs them into structs, and compare with forge test --gas-report. Explain the difference using evm.codes to look up the exact opcode costs. Seeing the gas drop when you pack four uint64s into one slot, and understanding why (one SSTORE instead of four), is the lesson that makes you write efficient contracts by reflex rather than by checklist.
