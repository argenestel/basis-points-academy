Solana security is mostly about account validation: proving that the accounts a program was handed are the ones it expected, from the right owner, of the right type, signed by the right party. Get the validation right and most Solana exploit classes are closed; miss a check and you get Wormhole or Cashio. Anchor, the standard framework, generates most of this validation from declarative constraints, which is why learning its constraints is learning Solana security. This lesson is that framework and the bug classes it defends against.

Anchor and constraints

Anchor lets you declare accounts and constraints, and it generates the validation, serialization, and an IDL (interface description) for typed clients.

#[derive(Accounts)]
pub struct Buy<'info> {
    #[account(mut)] pub buyer: Signer<'info>,                                  // must sign
    #[account(mut, seeds = [b"curve", mint.key().as_ref()], bump = curve.bump,
              has_one = mint, has_one = creator)] pub curve: Account<'info, Curve>, // owner + discriminator checked
    pub token_program: Program<'info, Token>,                                 // must be the real Token program
}

Read what the constraints enforce: Signer requires the buyer actually signed; the seeds/bump verify the curve is the canonical PDA for that mint (Unit 23 lesson 1); has_one checks the curve's stored mint and creator match the passed accounts; Account<Curve> checks the owner and an 8-byte discriminator (so a fake account with the same layout is rejected); and Program<Token> ensures the token program is the real one, not an attacker's. Each constraint closes a specific bug class.

The classic Solana bugs

  • Missing signer check: if you don't require Signer, anyone can act for anyone.
  • Missing owner or type check ("account substitution" / "type cosplay"): an attacker passes a fake account with the same byte layout. Account<T> defends by checking the owner and an 8-byte discriminator, without it, your program reads the attacker's data as if it were real.
  • Arbitrary CPI: calling whatever "token program" the user passed instead of the real one. Program<Token> defends.
  • Non-canonical PDA bumps, reinitialization, and closed accounts being revived: subtler lifecycle bugs that Anchor constraints and careful account handling address.
  • Integer overflow in release builds unless overflow-checks = true. Rust's release mode doesn't check overflow by default, use checked math.

Wormhole and Cashio: missing validation

The two famous Solana losses were both missing-validation bugs, exactly the classes above. Wormhole (Feb 2022, ~$325M) accepted a spoofed system account in its signature verification, an account-substitution bug: it trusted an account it should have validated (Unit 12). Cashio (Mar 2022, ~$48M) didn't validate the chain of collateral accounts, so fake collateral minted real stablecoins, a missing has_one-style check on the account relationships. Neither was a cryptographic failure; both were a program trusting an account it was handed without checking it was the right one. This is why Anchor's constraints matter so much: they make the checks declarative and hard to forget, and the biggest Solana hacks are what happens when the checks are absent.

Build it

In the solana-launchpad lab, remove has_one = creator from the Sell instruction and write a TypeScript test where a seller passes their own wallet as creator to steal the fee. Then restore the constraint and show the test fails. Deliberately removing one constraint and watching the exploit work, then restoring it and watching it fail, is the most direct way to understand that on Solana a single missing has_one is the difference between safe and drained, which is precisely the lesson of Wormhole and Cashio in miniature, on your own program.
