Blockchains are islands. Chain B has no way to directly observe what happened on chain A; it only knows its own state. So every bridge, no matter how it's marketed, is fundamentally an answer to one question: who tells B what happened on A, and why should B believe them? The different answers are the different trust models, and since bridges are where the largest hacks in crypto happen (Unit 12 lesson 4), getting this question right is the difference between a bridge and a honeypot.

The core problem

To mint a wrapped token on B, or release funds on B, the bridge contract on B must be convinced that a corresponding lock or burn really happened on A. But B can't check A directly. Something, or someone, has to attest to it, and that attestation is the entire security of the bridge. Everything else is detail.

Four trust models

How B is convinced it happened on A

Externally verifiedan m-of-n set of signers (multisig, MPC, guardians, DVNs, oracle networks) attestsWormhole (19 guardians), LayerZero DVNs, CCIP, Axelar — trust an honest threshold of the signer set
Natively verifieda light client of A runs on B, verifying A's consensus signatures and Merkle proofsIBC, ZK light-client bridges, rollup canonical bridges — trust A's consensus itself
Optimisticmessages accepted after a challenge window unless a watcher proves fraudNomad (historical), Across settlement — trust that at least one honest watcher exists
Locally verifiedthe two counterparties check each other directlyatomic swaps, HTLCs — trust only the two parties

The trade-off they all make

These models trade trust minimisation against cost, generality and latency:

  • Native (light client) is the strongest: B verifies A's actual consensus, so you trust only the same thing A's own users trust. But running a light client of A on B is expensive (you're verifying A's signatures on B's execution), and it's chain-specific (a light client of Ethereum doesn't help you bridge from Solana). ZK compression of the light-client proof is the active frontier.
  • External (m-of-n) is cheap and general: the same signer set can bridge any chains, and verification is just checking signatures. But you've added a new trust assumption, the honesty of the signer set, that didn't exist before, and that's where the hacks happen (lesson 4).
  • Optimistic is cheap but slow: you accept messages by default and allow a window for fraud proofs, so you trust that one honest watcher is paying attention, and you wait out the window.
  • Local is the most trust-minimised but the least general: it only works for direct swaps between two parties, not arbitrary messaging.

The deeper point: bridged assets inherit the source chain's security

Vitalik's multichain argument: even a perfect light-client bridge, with zero verification risk, inherits the security of the source chain. If chain A gets 51%-attacked (Unit 2), an attacker can create a fake lock event on A, and a perfect bridge will faithfully relay it to B, minting unbacked tokens. The bridge did its job correctly; A lied. So bridged assets from a weakly-secured chain are only as safe as that chain, no matter how good the bridge is. This is why bridging from small proof-of-work chains is dangerous, and why "cross-chain" composability has a security ceiling set by the weakest chain involved.

Build it

Classify eight bridges you've used or heard of into the four models. For each, write down the exact set of parties whose collusion or compromise could steal funds: which signers, which watchers, which chain's validators. This exercise is uncomfortable, because for many popular bridges the answer is "a small multisig," and seeing it written plainly is the point. It's the cost-of-attack inequality from Unit 1 applied to the thing that holds the most money in crypto.
