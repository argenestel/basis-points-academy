Every frontend and every bot needs to talk to contracts, and viem is the TypeScript library most of them use. The important thing isn't the API surface; it's one pattern, read then simulate then write then wait, that catches stale state and gives users readable errors instead of failed transactions they paid for. This lesson is viem's core ideas and that pattern, which applies equally to a trading UI and a liquidation bot (Unit 11).

The core ideas

  • Three clients: a public client for reads, a wallet client for signing, and a test client for anvil's cheat methods (Unit 5).
  • Typed ABIs: declare an ABI as const and viem checks function names, argument types and return types at compile time. A typo becomes a compile error, not a runtime failure.
  • Everything is bigint: token amounts are huge integers, never JS floats. Use parseUnits and formatUnits to convert, and never a float, because floating-point rounding on a token amount is a bug waiting to lose money (Unit 2).

The read-simulate-write-wait pattern

The one pattern to internalise, because it's what separates a robust integration from one that pays gas for failures:

const { request } = await pub.simulateContract({
  address: pair, abi, functionName: "swap",
  args: [0n, minOut, me], account        // throws with the reason ("K") if it would revert
})
const hash = await wallet.writeContract(request)
const receipt = await pub.waitForTransactionReceipt({ hash })
  • Read (readContract) for views: get the current reserves, your balance, the price.
  • Simulate (simulateContract): run the call against current state and either get a prepared request or a thrown, decoded revert reason. This is the crucial step.
  • Write (writeContract): send the prepared request.
  • Wait (waitForTransactionReceipt): confirm it landed.

Always simulate before sending

Simulation is free, and it catches the two things that cost users money and trust: a stale quote (the price moved since you read it, so the swap would revert on slippage) and any other revert condition, returned as a decoded reason ("K", "insufficient output") rather than an opaque failure. A frontend that simulates can tell the user "this would fail because the price moved" before they pay gas; one that doesn't lets them pay for a reverted transaction. The same is true for bots (Unit 11): simulate against the exact pending state, because the opportunity may have vanished since you spotted it. Simulate-before-send is not an optimisation; it's the difference between a tool that respects the user's gas and one that burns it.

Events

For history and live updates, getContractEvents fetches past events and watchContractEvent streams new ones, the client-side counterpart to the log-reading in Unit 16. A price chart is a stream of Swap events; a bot's state mirror (Unit 11) is built by watching the events that change the state it tracks.

Build it

Run the dapp-viem lab (npm test) against the AMM lab's contracts on a local chain. Then add a quote endpoint that returns amountOut, price impact and the minimum out for a slippage setting (Unit 6), and a script that streams Swap events into a price chart. Building the quote endpoint forces you to use read-and-simulate correctly, and streaming events into a chart is the live-data pattern every dApp and dashboard needs. The lab does deploy, quote, slippage-protected swap, decoded reverts and event history, which is the full client side of a DeFi app in miniature.
