The same handful of bug classes drain protocols year after year, which is good news for a defender: the list is short and the defences are known. This lesson is that catalogue, each class paired with a recent example and, crucially, with the test that would have caught it before deployment. It's written for the person building the protocol, not attacking it: the goal is to recognise your own code in this table and write the failing test first.

Reading the catalogue

Three patterns are worth pulling out, because they're where defenders are most often caught off guard.

  • Rounding bugs compound in batches. A one-wei error is invisible in a unit test and decisive when an attacker loops it hundreds of times in a single batched transaction (Balancer, Unit 6). The defence isn't "round carefully" in the abstract; it's high-iteration invariant fuzzing with tiny amounts and adversarial ordering (Unit 5), because that's the only thing that surfaces a rounding error before an attacker does.
  • Old code still holds money. Truebit's contract had been live for about five years when a legacy integer-overflow bug (from before Solidity 0.8's checked math) was exploited. "It's been fine for years" is not safety; it's exposure that hasn't been collected yet. Re-audit old code, especially pre-0.8 arithmetic.
  • Never forward arbitrary calldata. If your contract lets a user specify a call for it to make, and the contract holds approvals, an attacker can direct it to transferFrom every wallet that approved it (SwapNet, Unit 5). Scope every call and every approval.

The practice that makes you good at this

Reproduce one exploit a week

The single most effective way to learn to defend is to reproduce real exploits. Take one incident a week from DeFiHackLabs (hundreds of real hacks as Foundry fork tests, Unit 18), fork to the block before the attack, replay it, and then write the invariant that would have failed before it happened. After a few months you'll recognise the shape of each bug class in your own code before you write it, which is the whole point. Before building anything that uses a given pattern (an oracle, a vault, a bridge), search Solodit for every exploit of that pattern first. The defender's edge is that the attacker's playbook is public.

Build it

Reproduce 4 exploits from DeFiHackLabs covering 4 different classes from the table, each against the historical contracts on a fork (the only legal place to run them, Unit 18). For each, add the invariant test (Unit 5) that would have failed before the attack. Four reproductions across four classes is enough to internalise the method: an exploit is a violated invariant that nobody wrote down, and your job as a builder is to write it down first.
