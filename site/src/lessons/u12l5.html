The best way to understand bridge security is to build the insecure version and then harden it, item by item, with a failing test written first for each weakness. The minimal bridge is a few lines. Everything that makes it safe, and everything from lesson 4 that its absence caused, is in the hardening. This lesson is that build, which is also the Unit 12 project and the capstone track D (Unit 17).

v0: the minimal bridge

// Chain A
function lock(uint256 amt, address to) external {
    token.safeTransferFrom(msg.sender, address(this), amt);
    emit Locked(nonce++, msg.sender, to, amt, block.chainid, DEST_CHAIN);
}
// Chain B
function mint(Message calldata m, bytes[] calldata sigs) external {
    bytes32 h = keccak256(abi.encode(m, SRC_CHAIN, address(this)));
    require(!consumed[h], "replay");  consumed[h] = true;
    require(verify(h, sigs) >= THRESHOLD, "sigs");   // sorted unique signers
    require(windowMinted + m.amt <= windowCap, "rate");
    windowMinted += m.amt;
    token.mint(m.to, m.amt);
}

This already contains, in miniature, several of lesson 4's lessons. Walk through why each line is there.

The hardening checklist

Each item below corresponds to an incident from lesson 4. Write the failing test first, then the fix.

  • Domain separation (replay protection). The hash commits to the source chain, destination chain, contract address and nonce, and each hash is marked consumed. Without all four, a message can be replayed on another chain, another deployment, or twice. This is Unit 2 lesson 1 and the June 2026 cross-chain replay incident.
  • Finality and reorgs. The relayer must wait for the source chain's finality (a finalised checkpoint, or N confirmations, Unit 2) before minting, and handle the case where the source reorgs after it saw the lock. Mint too early and a reorged-away lock mints unbacked tokens.
  • Independent verifier set. m-of-n signers with sorted, unique addresses, key rotation behind a timelock, and operators on independent infrastructure (Ronin fell because four keys were one operator's). The upgrade path is toward light-client or ZK verification (lesson 1).
  • Rate limits. A cap per time window and per transfer size, with large transfers delayed. This is the single feature that would have bounded nearly every hack in lesson 4.
  • Watchers. Independent off-chain processes that compare locked-on-A with minted-on-B and can trigger a pause when they diverge.
  • Pause and recovery. A guardian can pause; upgrades are timelocked; the incident runbook is written before the incident, not during it (Unit 15).
the invariant a watcher enforces: Σ minted(B) ≤ Σ locked(A) alerting within one block of any violation

If minted ever exceeds locked, something has forged a message. A watcher that checks this every block and can pause is the backstop behind all the other defences.

Build it

Build v0 with two anvil instances and a Rust or TypeScript relayer running 3 signers (2-of-3). Then add each hardening item, writing the failing test first: a replay across chains, a reorg on the source, a compromised signer, a rate-limit breach, and a watcher-triggered pause. By the end you'll have re-derived every lesson from the hack history by watching your own bridge fail and then fixing it, which is the only way to internalise that a bridge's security is the hardening, not the happy path.
