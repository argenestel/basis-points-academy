The capstone is where the whole course becomes one project. Rather than build something generic, you pick one of six tracks, each a real protocol type, and follow a milestone path that pulls together the exact units you need. The discipline is to go deep on one rather than sample several, and to ship runnable, tested code at every milestone, because a protocol that doesn't run at each step isn't a protocol, it's a plan.

Why these tracks

Each track is a complete, real protocol type that you've now studied the pieces of, and each milestone is something you learned to build in an earlier unit. Track A's margin engine is Unit 9's lab; its order book is Unit 3's capstone; its MM program is Unit 13. Track E's stability pool is Unit 8's lab; its depeg stress tests are Unit 15. The tracks are designed so that the capstone isn't new material, it's the assembly of material you already have, into something that holds other people's money. That assembly is the skill the course is actually teaching.

Pick one, go deep

The temptation is to sample several tracks shallowly. Resist it. A perp DEX built properly, with a real margin engine, a tested liquidation waterfall, and a working oracle, teaches you more than three half-built protocols, because the depth is where the hard interlocks show up (the ones the design canvas, lesson 1, warned you about). Pick the track whose domain you most want to work in, and build it until it runs end to end.

Build it

Choose your track and write a 12-week plan with one demoable milestone every two weeks. Put it in your repo's README. A plan with dated, demoable milestones is what turns "I'm building a perp DEX" into a project you actually finish, and the Builds tab has detailed checklists for each track's pieces, with your progress saved. The two-week demoable cadence is deliberate: it forces runnable code at every step, which is the rule that separates shipped protocols from abandoned ones.
