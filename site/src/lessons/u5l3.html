Here is a fact that should reshape how you think about smart-contract security: in 2025 and 2026, the largest losses were not clever exploits of contract logic. They were compromises of the people and keys that controlled the contracts. A protocol can have flawless math and still lose everything if one admin key is phished. This lesson covers the machinery of upgradeability and access control, and then the controls that actually reduce the risk that dominates the loss statistics.

Proxies: separating storage from logic

To upgrade a contract you separate what it stores from what it does. A proxy holds the storage and the funds and delegates all calls to an implementation contract that holds the logic; to upgrade, you point the proxy at a new implementation. The patterns:

  • Transparent proxy. The admin's calls go to the proxy's own admin functions; everyone else's are delegated to the logic. Simple, slightly more gas.
  • UUPS. The upgrade function lives in the implementation, not the proxy. Cheaper, but if you deploy an implementation without an upgrade function, the proxy is frozen forever.
  • Beacon. Many proxies point at one beacon that holds the implementation address, so you upgrade all of them at once.
  • Diamond (EIP-2535). Many implementation "facets" behind one proxy, for contracts too big for the size limit.

The classic proxy bugs

Storage collisions: because the proxy and implementation share the proxy's storage slots, a new implementation that reorders or inserts a variable will read garbage from the old layout. Use ERC-7201 namespaced storage so each module's variables live at a hashed, collision-resistant slot. Uninitialized implementations: the implementation contract itself can be initialized by anyone if you forget to lock it, and for UUPS that let an attacker become its owner and selfdestruct it, bricking every proxy pointing at it (the first Parity multisig freeze, 2017, was this class). Always call _disableInitializers() in the implementation's constructor.

Access control is the real attack surface

The loss table of the last two years is dominated not by reentrancy or oracle bugs but by compromised authority:

Bybit, Feb 2025, ~$1.5Bthe Safe wallet UI the signers used was compromisedsigners approved a malicious transaction they couldn't see was malicious

None of these was a flaw in the contract math. The contracts did exactly what their legitimate-looking instructions told them to. The failure was upstream, in who could give instructions and how those instructions were verified.

Controls that actually help

Given that authority is the risk, the controls that matter are the ones that make a single compromised key insufficient and a malicious instruction visible before it executes.

  • Timelocks. Upgrades and parameter changes wait N days before they take effect, so users can see them coming and exit, and the team can cancel a malicious one. A timelock turns an instant theft into a public, delayed attempt.
  • Multisigs with independent signers. Several signers on separate hardware, in separate places, who each independently decode and verify the calldata, rather than trusting the UI. Bybit happened because the signers trusted what the screen showed; the defence is to verify the raw transaction against an independent tool (the build exercise below).
  • Role separation. The key that can pause is not the key that can upgrade is not the key that can move the treasury. One compromised role then can't do everything.
  • Rate limits and outflow caps. A cap on how much can leave per time window turns a total drain into a bounded one and buys time to respond.
  • Monitoring with automatic pause. Anomaly detection on flows and invariants, wired to an automatic pause on critical signals (Unit 15).
  • Minimise, then remove. Every admin power is a liability. The mature endpoint is immutability: contracts that nobody, including the team, can change. Uniswap v4's PoolManager and Morpho Blue's core are immutable by design (Unit 19).

Build it

Deploy a UUPS-upgradeable contract behind an OpenZeppelin TimelockController owned by a 2-of-3 Safe on a local fork. Then write the script that matters most: one that decodes and prints the calldata of a pending upgrade (the target, the function, the decoded arguments) so signers can verify independently of any UI what they're about to approve. That script is the control that would have stopped Bybit. Building it teaches the lesson better than reading about it: the security of a multisig is only as good as the signers' ability to see what they're signing.
